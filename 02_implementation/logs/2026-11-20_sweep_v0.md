# 독립 Sweep v0 구현과 검증

## 요청·정정·기준

사용자는 `inspire_sweep_only_v2_test_action_penalty_linear_reach`를 기능 기준으로 새 파일의 새 환경을 요청했다. 요청 차이는 방향별 접촉면 Sweep 계수, 5개 커리큘럼 고정화, 관측 전용 F/T 정규화다.

후속 정정 두 가지를 최종 구현에 반영했다.

- Deadzone은0° 유지. 구역을90°씩 나누지 않고 Pull/Push(12시/6시)는 각60°, 좌우는 나머지 각120°로 분류한다.
- 긴 v3 접미사를 추가하는 계열 대신 **별도 파일의 독립 계통**으로 선언한다. 최종 task=`Inspire-Sweep-v0`, experiment=`inspire_sweep_v0`다.

기준 코드 HEAD는 `30b499a427b0b14f3d07a3edc9642801a37c5eb2`, 문서 저장소 HEAD는 `db140e6b428ceb13744e058374274ebc781051da`다. 시작 시 문서 submodule 변경, 이전 wr7 진단 문서, 사용자 `docs/plan/PLAN19.md`가 있었다. 이 변경과 학습 로그를 보존했다.

## 구현 위치

- `envs/sweep_v0_envs.py`: 독립 전체 환경 구성, 요청한 계수·고정값·관측 scale.
- `agent/sweep_v0_ppo_cfg.py`: 기존과 같은 PPO 값의 독립 선언과 새 로그 이름.
- `runtime/sweep_v0.py`: 새 runtime entry point. 기존 step/reset 코드를 복제하지 않는다.
- `mdp/reward_functions/sweep_contact_preference.py`: episode 방향의 선반 기준 구역 분류, 타겟 전용 접촉면 하중, Sweep 계수.
- `__init__.py`: 새 Gym 등록 하나 추가.
- `tests/test_sweep_v0.py`: 구역 경계·8조합·혼합·미분류·불량 파라미터·선반 회전·타겟 필터·실제 표면 mapper 검사.
- `scripts/check_sweep_v0.py`: 전체 설정·관측 manager·물리값 보존·GPU reset/step/부분 reset 검사.

## CPU 검증

```bash
CUDA_VISIBLE_DEVICES='' OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
  PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 \
  /home/min/miniconda3/envs/env_isaaclab/bin/python -m pytest \
  src/inspire_sweep_baseline/tests/test_sweep_v0.py \
  src/inspire_sweep_baseline/tests/test_sweep_only_action_penalty.py \
  src/inspire_sweep_baseline/tests/test_stabilize_sweep.py -q
```

최종 **116 passed / 8.35초**다. 신규8개, 기존 ActionPenalty/LinearReach13개와 Stabilize/Sweep95개를 함께 실행했다. 실제 `PairedContactRegions`에 앞면1N·뒷면3N의 타겟 접촉과1000N 장애물 접촉을 제공하고, 직접 타겟 pad5N을 합친 결과가 손바닥6N·손등3N임을 확인했다. 장애물은 섞이지 않으며 원본 contact counts/starts와 reset 행이 보존된다. CPU 샘플은 입력 기하를 제어한 검증이며 실제 PhysX 접촉을 발생시킨 결과는 아니다.

최초 단위 검사에서 검사용 pad 필터를1개만 제공하여17채널로 broadcast된 fixture 오류가 있었다. 실제 구조와 같이17개 필터를 제공하도록 검사 데이터를 수정한 후 통과했다. production 구현의 pad 필터는 처음부터17개다.

## GPU 검증·전체 대조

과거 사용자 허용 범위의 GPU smoke를 수행했다. 시작 시 RTX3090은 약497MiB 사용 중이었다. 학습은 시작하지 않았다.

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
  /home/min/miniconda3/envs/env_isaaclab/bin/python -u \
  src/inspire_sweep_baseline/scripts/check_sweep_v0.py --headless
```

최종 `Inspire-Sweep-v0`의 결과는 **cuda:0, seed42, 4환경, 8step, 부분 reset·추가1step 통과**다. 결과는 [smoke JSON](../../../../outputs/sweep_v0/smoke.json), stdout은 임시 파일 `/tmp/check_sweep_v0.log`다.

1. Registry의 실제 config를 import하고 전체 `to_dict()`를 비교했다. Sweep term, 장애물/wrench 값, curriculum 제거, 관측 scale을 기준값으로 복원한 비교 사본은 기준 환경 전체 dict와 같다. 기존 기준 환경의 인스턴스·새 인스턴스도 원래 dict와 같다.
2. 새 EnvCfg/PPO Cfg의 직접 부모가 각각 Isaac Lab 기반 Cfg임을 확인했다. 실제 PPO dict는 experiment name을 제외하면 기준과 같다.
3. RewardManager 활성15개, CurriculumManager 활성0개, Deadzone0°, 관측66D+64D, action12D를 확인했다.
4. 실제 ObservationManager에 물리 단위의 제어된 값을 공급하여 clip 후 scale을 검증했다. 300N/16Nm는 관측1로 제한되고 물리 공급 tensor는 바뀌지 않는다. wr7 실패의 F/T 입력도 약 `[.04573,.25075,.11343,-.59175,.10075,-.02825]`가 된다.
5. 동일 물리 callable을 읽는 실제 `WrenchMagnitudeChangePenalty` 이력에 원래300N/16Nm를 포함한 값이 남음을 확인했다. 관측 clip 밖의 물리값도 reward 경로에서 보존된다.
6. 8step 동안 양의 Sweep manager 값이 함수×50이고 전체 보상은 가중 term 합×dt임을 확인했다. 기존 ActionPenalty·Reach·retreat에 별도 계수를 적용하지 않는다.
7. 선택 행 부분 reset에서 다른 행의 물체 상태가 보존되고 이후 step의 관측·보상이 유한했다. 새 표면 하중 함수도 live scene에서 유한·비음수 값을 반환한다.
8. HEAD의 기존 등록 AST 전체와 현재 prefix가 동일하고 마지막 등록 하나만 추가됐음을 확인했다. 기존 환경 소스는 변경하지 않았다.

네이밍 정정 전 임시 직접 자식 구성으로도 동일 smoke를 통과했으나, 위 결과는 **정정 후 독립 `SweepEnvCfg`와 최종 ID로 다시 실행한 결과**다. 임시 v3 등록·소스 파일은 최종 트리에 남기지 않았다.

## 영향과 미검증

기존 LinearReach·Sweep Only·Holding·Final task에는 변경이 없다. 모델 구조와 PPO hyperparameter·수치 보호 한도도 바꾸지 않았다. 정규화로 기존 정책 입력의 의미가 달라지지만 새 로그 디렉터리로 별도 학습하도록 구성했다.

실제 장기 학습·방향별 접촉면 선호 개선·발산 방지율·2048환경 성능은 검증하지 않았다. 짧은 rollout은 특정 손바닥/손등 접촉 행동의 성공을 증명하지 않는다. 접촉면 분류는 기존 tactile footprint의 양면과 직접 pad로 정의되므로 미분류 모서리 접촉은 계수1이다.
