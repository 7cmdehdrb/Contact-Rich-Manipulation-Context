# 접촉 표현과 Sweeping 정책의 입출력

[발표 문서 안내](README.md) · [태스크와 프레임워크](02_Task_Definition_and_Framework.md) · [보상 설계](04_Reward_Formulation.md) · [성공과 종료](05_Success_and_Termination.md)

기준일: **2026-10-05**. 주 근거는 `중간발표_최종.pdf`의 **실제 PDF 17–21쪽과 29쪽**이다. 전체 시스템과 학습·실행 구분에는 14–16쪽도 참조한다. PDF 하단에 인쇄된 슬라이드 번호는 실제 PDF 쪽수와 다르므로, 이 문서의 쪽수는 34쪽 파일에서의 순서를 뜻한다.

> **문서 상태: 최종 중간발표 자료에 제시된 설계 설명.** 57차원 관측, 8차원 행동과 제어 경로를 설명하며, 센서 실측 성능·현재 학습 코드·실물 동작의 검증 완료를 뜻하지 않는다. 최종 PDF가 변경한 표현은 과거 초안보다 우선하고, PDF에서 결정하지 않은 구현 세부는 미정으로 남긴다.

## 1. 접촉 피드백으로 무엇을 알아야 하는가

초기 시각 관측은 물체의 출발 위치를 제공한다. 그러나 Sweeping이 시작된 뒤에는 물체의 현재 위치·자세를 시각으로 계속 갱신하지 않는다. 따라서 정책은 자신이 어떤 자세로 움직였는지, 손의 어느 영역에 접촉이 남아 있는지, 손목으로 전달되는 하중이 어떻게 달라지는지를 함께 사용하여 다음 행동을 결정해야 한다.

이때 이진 촉각과 손목 F/T는 서로 다른 물리량을 표현한다. 촉각은 **어느 영역이 닿았는가**를 알려주고, F/T는 **어떤 크기와 방향의 하중이 전달되는가**를 알려준다. 동일한 접촉 영역이 활성화되어도 힘의 크기나 모멘트는 달라질 수 있고, 비슷한 손목 합력 아래에서도 활성 촉각 영역은 달라질 수 있다. 두 센서를 함께 쓰는 이유는 이러한 차이를 정책이 이용하도록 하기 위해서다. [PDF 17쪽]

| 정보 | 정책에 제공하는 물리적 의미 | 이 정보만으로 확정할 수 없는 것 |
| --- | --- | --- |
| Binary Tactile | 선택한 손 면의 영역별 접촉 여부, 접촉 유지·소실, 활성 영역의 변화 | 각 영역의 연속적인 하중 크기, 정확한 접촉점, 현재 물체 Pose |
| Wrist F/T | 손목으로 전달되는 3축 힘과 3축 모멘트 | 각 영역의 개별 접촉력, 다중 접촉의 원인과 물체별 분해 |
| 로봇·Hand 상태 | 자신의 관절 상태와 Hand Pose, 현재 손 모양 | Hand 이동이 그대로 물체 이동이 되었다는 사실 |
| 초기 위치와 목표 명령 | 출발 물체 위치와 요구되는 이동 방향·거리 | 실행 중 물체의 실제 진행 상황 |

최종 PDF는 촉각을 **Coarse Contact Information**, F/T를 **Fine Load Information**으로 표현한다. 이는 촉각의 공간 영역 표현이 거칠고 F/T 하중 값이 연속적이라는 뜻이다. F/T가 물체의 공간 위치를 직접 정밀 관측한다는 의미는 아니다.

## 2. 18차원 이진 촉각 표현

### 2.1. 접촉면과 영역별 접촉을 분리한다

촉각 관측은 손바닥·손등 중 어느 면을 사용하는지 나타내는 Header 1개와, 선택한 면의 고정된 17개 영역에 대한 접촉 값으로 구성한다. [PDF 19쪽]

```math
\mathbf{T}_t=[T_{\mathrm{header},t},T_{1,t},\ldots,T_{17,t}]
\in\{0,1\}^{18}.
```

| 성분 | 의미 | 최종 PDF의 표현 |
| --- | --- | --- |
| $T_{\mathrm{header},t}$ | 사용하는 접촉면을 구분하는 값 | 그림에서 0은 손바닥, 1은 손등 |
| $T_{i,t}$ | 선택한 면의 $i$번째 촉각 영역 접촉 여부 | 접촉 감지 시 1, 미감지 시 0 |

Header는 접촉이 발생했다는 표시가 아니다. 예를 들어 Header가 1이고 나머지 17개 값이 모두 0이면, 손등을 사용하는 작업에서 해당 영역들의 접촉이 감지되지 않은 상태로 해석한다. 접촉 영역 수를 계산할 때도 Header를 포함하지 않는다.

항상 고정된 17개 인덱스의 0과 1을 전달해야 한다. 현재 활성화된 센서 값만 모으면 벡터 길이와 위치 의미가 달라져, 정책이 접촉 위치의 변화를 일관되게 해석할 수 없다.

### 2.2. 원시 센서와 정책 표현은 다르다

과거 [Method 초안](1st_draft/03_Method.md#surface-conditioned-tactile)과 [9월 30일 연구 요약](2026-09-30_midterm/midterm_summary.md)은 손바닥의 17개 촉각 영역과 손등에 부착할 17개 FSR을 대응시키고, 선택한 작업면의 관측을 사용하는 설계를 설명한다. 손바닥 Grid는 영역 내부의 감지 결과를, 손등 FSR은 해당 센서의 신호를 Binary 값 하나로 축약하는 방향이다.

따라서 18차원은 실제 센서 전체의 원시 출력 차원이 아니라 **정책이 받는 가공된 표현의 차원**이다. 실제 센서와 시뮬레이션의 영역 대응, 영역별 감지 임계값과 전처리는 별도 확인이 필요하다. 최종 PDF는 Binary 벡터를 정의하지만 이진화 임계값의 수치나 실물 보정 결과를 제시하지 않는다.

[이전 발표 정리본](2026-09-30_midterm/README.md#sensing)은 **0.05 N**을 설계값으로 기록하며, 손바닥 영역은 내부 Cell 중 하나라도 임계값 이상이면 활성화하고 손등 FSR은 임계값 초과로 표기한다. 이 값은 이전 발표의 설정으로 보존하되, 최종 PDF에 재명시된 수치나 실물 성능을 검증한 임계값으로 해석하지 않는다. 두 면의 경계값 처리 통일과 현재 구현의 적용값은 확인 대상이다.

손바닥과 손등을 모두 독립적인 17차원 벡터로 넣는 구성은 현재의 18차원 정의와 다르다. 선택 면 하나로 표현하는 설계에서 양면 동시 접촉, 비선택 면의 접촉, Header 전환을 어떻게 처리할지는 구현 전에 정해야 한다. 모두 0인 촉각 관측만으로 정상 무접촉·약한 접촉·비센서 부위 접촉·센서 누락을 구분할 수도 없다.

## 3. 6차원 손목 Wrench와 물리적 결합

F/T 관측은 힘 3성분과 모멘트 3성분을 함께 사용한다. [PDF 19쪽]

```math
\mathbf{F}_t=[F_{x,t},F_{y,t},F_{z,t},M_{x,t},M_{y,t},M_{z,t}]
\in\mathbb{R}^{6}.
```

여기서 PDF의 $\mathbf{F}_t$는 힘만이 아니라 6축 Wrench 전체를 뜻한다. 힘과 모멘트는 물리 단위가 다르므로 정규화와 크기 제한도 성분의 의미에 맞춰 정의해야 한다.

시뮬레이션 프레임워크는 손목의 Reaction Wrench를 가상 F/T 입력으로 사용하는 경로를 제시한다. 과거 연구 요약은 센서 장착 위치에 둔 측정용 Fixed Joint를 통해 반력·모멘트를 얻는 구성을 설명한다. 이러한 손목 신호는 대상 물체와의 접촉 외에 손의 중량, 동작에 따른 부하, 다른 접촉의 영향도 포함할 수 있다. 따라서 영점·부하 보정, 측정 좌표계와 모멘트 기준점의 정의를 확인해야 하며, 원시 손목 신호를 대상 물체의 접촉력 정답과 동일하게 취급하지 않는다. [PDF 15쪽; 9월 30일 연구 요약]

물리적 결합은 촉각 활성 영역으로 대략적인 접촉면을 파악하고, 힘–모멘트 관계를 이용해 그 면에서의 하중 작용 위치, 즉 CoP를 추정하는 방향이다. 접촉 영역은 위치 후보를 제한하고 Wrench는 하중에 관한 연속적인 정보를 제공한다. [PDF 17쪽]

CoP는 현재 물체 Pose의 직접 관측값이 아니다. 추정에 사용하는 접촉면과 Wrench 좌표·기준점이 일치해야 하며, 여러 접촉이 동시에 발생하면 하나의 점으로 해석하는 조건을 검토해야 한다. 최종 관측식에는 별도의 CoP 성분이 추가되어 있지 않다. CoP 변화로 회전 Sub-Goal을 만들고 보상에 사용하는 내용은 [보상 설계](04_Reward_Formulation.md)에서 설명한다. [PDF 21·27쪽]

## 4. 전체 Actor 관측은 57차원이다

최종 PDF는 고유감각, 접촉 센서, 목표 조건, 직전 행동을 연결하여 하나의 정책 입력 벡터로 사용한다. [PDF 18–21쪽]

| 묶음 | 성분 | 차원 | 역할 |
| --- | --- | ---: | --- |
| Proprioception | Manipulator Joint Position $\mathbf{q}_{r,t}$ | 6 | 현재 팔 관절 배치 |
| Proprioception | Manipulator Joint Velocity $\dot{\mathbf{q}}_{r,t}$ | 6 | 현재 팔 관절 움직임 |
| Proprioception | Hand Pose $\mathbf{p}_{h,t}$ | 6 | Base Link 기준 위치 3 + 자세 3 |
| Proprioception | Hand State $\mathbf{q}_{h,t}$ | 2 | 정규화된 공통 굽힘·엄지 별도 상태 |
| Sensor | Binary Tactile $\mathbf{T}_t$ | 18 | 작업면 Header 1 + 접촉 영역 17 |
| Sensor | Wrist Wrench $\mathbf{F}_t$ | 6 | 힘 3 + 모멘트 3 |
| Goal | $\mathbf{g}$ | 5 | 초기 물체 위치 3 + 명령 거리 1 + 방향 1 |
| Last Action | $\mathbf{a}_{t-1}$ | 8 | 직전 Arm 6 + Hand 2 |
| **합계** | **20 + 24 + 5 + 8** | **57** | **최종 PDF의 Actor 입력 설계** |

```math
\mathbf{O}_t=\mathrm{col}\left(
\mathbf{q}_{r,t},\dot{\mathbf{q}}_{r,t},\mathbf{p}_{h,t},\mathbf{q}_{h,t},
\mathbf{T}_t,\mathbf{F}_t,\mathbf{g},\mathbf{a}_{t-1}
\right)\in\mathbb{R}^{57}.
```

이 차원에는 EEF Twist, Hand Joint Velocity, 현재 물체 위치·자세, 물체 Shape·Size, 명시적인 CoP 추정값을 추가하지 않는다. 해당 성분을 넣으면 발표에서 정의한 57차원과 다른 정책이 된다.

### 4.1. 고유감각 20차원

팔의 관절 위치·속도 12차원과 Hand Pose 6차원, Hand의 저차원 상태 2차원을 합쳐 20차원을 만든다. Hand Pose는 최종 PDF에서 **Base Link 기준**으로 표기되어 있으며, 위치와 roll·pitch·yaw에 해당하는 세 자세 성분으로 나타낸다. [PDF 18쪽]

Hand 상태는 다음 두 값이다.

```math
\mathbf{q}_{h,t}=[\bar q_{\mathrm{flex},t},\bar q_{\mathrm{thumb},t}]
\in[0,1]^2.
```

첫 값은 공통 손가락 굽힘 상태, 두 번째 값은 엄지의 별도 관절 상태를 나타낸다. 전체 손의 각 관절을 독립적으로 관측하는 구성은 아니다. 여러 굽힘 관절에서 대표 상태 하나를 만드는 집계 방식과 각 관절의 정규화 범위는 PDF에 명시되지 않는다.

### 4.2. 목표 조건 5차원

목표 조건에는 최초 관측한 물체 위치와 이동 거리·방향이 들어간다. 이 값은 실행 중의 물체 현재 위치를 새로 측정한 것이 아니다. [PDF 20쪽]

```math
\mathbf{g}=[p_{x,0}^{\mathrm{target}},p_{y,0}^{\mathrm{target}},
p_{z,0}^{\mathrm{target}},d_{\mathrm{cmd}},\theta_{\mathrm{cmd}}]
\in\mathbb{R}^{5}.
```

물체 위치와 목표 조건은 최종 PDF의 표기대로 Base Link 기준이다. 명령 방향의 기준축·양의 회전 방향·단위, 각도 경계 처리, 정규화 방식은 구현 시 명시해야 한다. 목표점 생성과 초기 관측 Noise의 의미는 [태스크 정의](02_Task_Definition_and_Framework.md)와 [보상 설계](04_Reward_Formulation.md)에서 연결한다.

### 4.3. 직전 행동 8차원

직전 행동은 정책이 이전 Step에 출력한 Arm Cartesian 증분 6개와 Hand 명령 2개다. 현재 접촉 변화가 직전 명령 뒤에 나타났다는 관계를 입력에서 함께 표현하며, 연속 행동 사이의 변화량을 억제하는 보상과도 연결된다. [PDF 20·26쪽]

직전 행동 하나의 포함은 여러 시점의 Observation Stack, Sliding Window 또는 RNN 채택을 뜻하지 않는다. 이력 기반 상태 추정이나 별도의 물체 Pose 추정기가 최종 Actor에 구현되어 있다고 해석하지 않는다. 최초 Step의 직전 행동 초기값과 Clip·Scale 적용 전후 중 어느 명령을 저장할지는 미정이다.

## 5. 실행 입력과 학습용 특권정보의 경계

정책 실행에서 사용할 수 있는 입력과 시뮬레이션이 학습·평가를 위해 알고 있는 정답은 구분해야 한다. 물체의 현재 상태를 Actor에 계속 제공하면 초기 시각 이후의 Blind 조건이 달라진다. [PDF 15·16·23·24쪽]

| 정보 | Actor의 실행 입력 | 학습·평가에서의 사용 |
| --- | --- | --- |
| 초기 물체 위치 | 사용 | 초기 목표 조건 구성. 초기 관측에는 Noise가 포함될 수 있음 |
| 현재 로봇·Hand 상태 | 사용 | 자신의 상태와 제어에 사용 |
| 현재 Binary Tactile·손목 Wrench | 사용 | 온라인 접촉 피드백과 센서 기반 보상에 사용 |
| 직전 정책 행동 | 사용 | 이전 명령 표현과 Action Rate 보상에 사용 |
| 현재 대상 물체의 정답 Pose | **사용하지 않음** | 목표 보상, 평가용 위치 오차·성공·전도 판정에 사용 가능 |
| 시뮬레이션의 대상 접촉력·접촉 법선 정답 | **사용하지 않음** | 접촉 방향 정렬 보상 등에 사용 |
| 물체별 접촉 ID·주변 물체 정답 | 최종 관측식에 없음 | 추가 활용 여부가 필요하면 실행 입력과 분리하여 명시 |

실측 손목 Wrench와 시뮬레이션의 정답 접촉력은 같은 3축 힘이 포함되어 있더라도 다른 정보다. 전자는 손목으로 전달되는 측정 신호이고, 후자는 대상 접촉을 구분해 얻을 수 있는 학습용 정보다.

최종 PDF는 PPO와 RSL-RL 학습을 제시하지만 Critic에 어떤 정보가 들어가는지는 명시하지 않는다. 특권정보를 보상에 쓴다는 설명만으로 Asymmetric Actor–Critic이나 별도 Teacher를 채택했다고 단정하지 않는다. 발표의 `MDP Formulation`이라는 절 제목도 57차원 입력만으로 실제 물체 상태가 완전히 관측된다는 주장으로 해석하지 않는다.

## 6. 8차원 행동과 저수준 제어의 역할

정책은 팔의 Cartesian 운동 명령과 손 모양을 정하는 명령을 동시에 출력한다. [PDF 29쪽]

```math
\mathbf{a}_t=\mathrm{col}(\mathbf{a}_t^{\mathrm{arm}},\mathbf{a}_t^{\mathrm{hand}}),
\qquad \mathbf{a}_t\in\mathbb{R}^{8}.
```

```math
\mathbf{a}_t^{\mathrm{arm}}=[\Delta p_{x,t}^{\mathrm{cmd}},\Delta p_{y,t}^{\mathrm{cmd}},
\Delta p_{z,t}^{\mathrm{cmd}},\Delta\theta_{x,t}^{\mathrm{cmd}},
\Delta\theta_{y,t}^{\mathrm{cmd}},\Delta\theta_{z,t}^{\mathrm{cmd}}],
\qquad
\mathbf{a}_t^{\mathrm{hand}}=[u_{\mathrm{flex},t},u_{\mathrm{thumb},t}].
```

| 출력 | 제어 대상 | 제어기가 담당하는 일 |
| --- | --- | --- |
| Arm 6D | EEF 기준 위치 증분 3 + 회전 증분 3 | Cartesian 명령을 팔의 관절 구동 명령으로 변환하여 실행 |
| Hand 2D | 공통 굽힘 목표 + 엄지 별도 관절 목표 | 두 제어 축을 실제 Hand 관절 목표로 매핑하여 실행 |

### 6.1. Arm: 정책은 증분을 정하고 OSC는 실행한다

Arm 출력은 직접적인 6축 관절 토크가 아니다. 정책은 Hand의 이동·회전 증분을 정하고, Operational Space Controller가 현재 로봇 상태를 이용해 이를 실행할 관절 토크로 변환한다. 접촉에 반응하여 어느 방향으로 얼마나 보정할지는 정책의 역할이고, 주어진 Cartesian 명령을 구동하는 일은 저수준 제어기의 역할이다.

시뮬레이션 경로는 `isaaclab.controllers.OperationalSpaceController`를 통해 6개 관절 토크를 계산하는 것으로 표시되어 있다. 실물 경로는 Pinocchio, 관절 토크, UR Driver를 연결하는 그림이며, 전체 프레임워크에서는 OSC Controller로 표시한다. 이는 계획된 실행 경로이고, 실제 UR 드라이버에서 해당 토크 명령이 동작했다는 검증 결과는 아니다. [PDF 15·29쪽]

Cartesian 증분을 목표 Pose에 누적하는 방법, 회전 증분의 적용 순서, Action Scale·Clip, OSC Gain과 Null-space 처리, 정책·제어 주기 및 실물 토크 전달 방식은 PDF에 명시되지 않는다. 해당 항목을 임의 수치로 채우지 않는다.

### 6.2. Hand: 두 제어 축으로 손 모양을 바꾼다

Hand의 두 값은 공통 굽힘과 엄지의 별도 움직임을 위한 정규화 목표 명령이다. 명령을 실제 관절 위치로 변환한 뒤, 시뮬레이션에서는 Joint Action 경로로, 실물에서는 Inspire Robot SDK 경로로 실행하는 설계다. [PDF 26·29쪽]

Hand State 2D는 현재 상태의 관측이고 Hand Action 2D는 원하는 상태의 명령이다. 같은 두 제어 축을 쓰더라도 측정값과 목표값을 구분한다. Arm의 여섯 값이 운동 증분이라는 이유로 Hand의 두 값까지 관절 증분으로 해석하지 않는다.

과거 [Method 초안](1st_draft/03_Method.md)은 공통 굽힘의 0을 Fully Closed, 1을 Fully Open으로 정의했다. 최종 PDF에는 이 두 끝점의 물리 의미와 실제 관절별 매핑이 재명시되지 않는다. 따라서 구초안의 정의와 실제 SDK·시뮬레이션 관절 방향을 대조하여 같은 입력이 같은 손 모양을 만드는지 확인해야 한다. 엄지의 어떤 관절을 제어하는지와 각 축의 관절 범위도 미정이다.

## 7. 학습과 실행에서의 정보 흐름

학습 환경은 센서에 대응하는 Binary Tactile·Reaction Wrench와 로봇 상태를 구성하고, 초기 목표 조건·직전 행동을 합쳐 57차원 관측을 만든다. 정책이 8차원 행동을 출력하면 Arm OSC와 Hand 관절 제어가 이를 실행한다. 변화한 물체 상태는 목표 보상과 종료 판정에, 변화한 접촉 신호는 다음 관측과 센서 기반 보상에 연결된다. PPO는 이러한 전이를 사용해 정책을 갱신하는 학습 방법이다. [PDF 15쪽]

실물 실행에서는 같은 의미의 고유감각·접촉 센서·명령·직전 행동을 제공하고, 학습된 정책의 Arm·Hand 출력을 각각 실제 제어 경로로 보낸다. 현재 물체 GT와 시뮬레이션 접촉 정답은 실행 입력에 들어가지 않는다. 도식의 Zero-Shot Deploy는 목표로 제시된 전이 경로이며, 실물 전이 성능이 확보되었다는 결과가 아니다.

이 구조는 별도의 물체 Pose를 명시적으로 복원하지 않고도 센서 변화에 반응하는 정책을 학습하려는 설계다. 어떤 신호에서 접촉 손실을 복구하고 어떤 신호에서 회전·손 모양을 보정하는지는 실제 정책 행동과 [센서 Ablation](06_Evaluation_and_Schedule.md)으로 확인해야 한다.
