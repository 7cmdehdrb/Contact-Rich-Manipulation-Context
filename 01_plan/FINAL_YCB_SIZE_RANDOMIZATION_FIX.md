## 1. 중앙 크기 기준 랜덤화와 바닥 정렬

현재 YCB 후보의 `size_fraction`은 `0.8/0.9/1.0`이다. **이 세 단계의 중앙은 0.9**이므로 YCB 기준 크기는 기존 정규화 형상의 `size_fraction=0.9`에 해당하는 크기로 잡는다. 이 중앙 형상을 새 기준 1.0으로 취급하고 그 위에 `U(0.9,1.1)`을 **한 번만** 적용한다. 원본 USD의 무보정 크기를 뜻하지 않는다. 기존 정규화 `size_fraction=1.0`에 대한 최종 비율로 표현하면 0.81~0.99다. 중앙 크기를 하나로 확정하는 보정과 무작위 배율 추출은 구별하며, 3단계 크기 추첨은 제거한다.

원통·직육면체·mug·bottle 등 절차적으로 생성하는 Mesh 물체도 각 형상의 기준 크기에 동일한 `U(0.9,1.1)` 등방성 배율을 적용한다. 이 물체들에 존재하지 않았던 YCB용 0.9 중앙 보정을 임의로 추가하지 않는다. X/Y/Z 독립 스케일링이나 직전 크기에 배율을 누적하는 방식은 사용하지 않는다.

- [ ] 8종의 최종 기준 치수와 bounds를 표로 확인하고, 기준 대비 실제 크기가 0.9~1.1배인지 검증한다. 생성·reset·캐시 사이의 중복 배율 적용을 제거한다.
- [ ] 배치·스폰에는 **최종 scale과 초기 자세를 적용한 실제 bounds**를 사용한다. 비대칭 mesh의 root와 bbox 중심 차이를 보정한다.
- [ ] 수평 선반에 upright/yaw로 배치할 때 root Z는 `surface_z - scaled_local_min_z`를 기준으로 정한다. 기울기를 허용하면 변환된 최저점을 사용한다. 일률적으로 root Z를 작업면 높이에 두거나 물체 높이의 절반을 더하지 않는다.
- [ ] collider의 실제 바닥이 작업면에 겹치거나 과하게 떠 있지 않은지 확인한다. 필요한 contact/rest offset의 여유는 측정해 최소한으로 정하고, 모든 물체에 임의의 큰 낙하 높이를 주지 않는다.
- [ ] visual·collider·배치 bounds·질량/관성 처리가 일치하는지, 처음 수 step의 침투·낙하·튀어오름·흔들림이 없는지 8종 및 크기 범위 끝값에서 검사한다.

## 2. 8종 가용성과 다양한 환경 경험

형상은 원통, 직육면체, mug, bottle, cracker box, sugar box, tomato soup can, master chef can의 8종이다. **타겟·Gray 장애물·White 장애물 모두 어느 형상이나 사용할 수 있다.** 역할별 형상 제외, 타겟과 같은 종류의 장애물 금지, 연속 동일 종류 금지 규칙을 추가하지 않는다. 동일 물리 인스턴스의 중복 역할 배정만 금지한다.

최신 지시에 따라 **특정 reset 규칙은 요구하지 않는다.** 매 reset 재생성, 선택적 재추출, 재사용 가능한 자산 등의 방식은 물리 안정성과 성능을 고려해 결정한다. 타겟 종류 확률을 반드시 1/8로 하거나 모든 물체를 매 reset 교체하는 조건은 필수가 아니다. 다만 종류·구성·배치·크기의 다양한 조합을 학습 전체에서 충분히 경험해야 하며, 구현 편의 때문에 일부 형상이 사라지거나 소수 고정 장면만 반복되어서는 안 된다. 균등 추출은 가능한 구현 선택이지 사용자 필수 룰은 아니다.

- [ ] 타겟과 장애물 양쪽에서 8종이 실제 등장하는지, 크기 0.9~1.1과 다양한 배치·구성의 커버리지를 충분한 환경·episode에서 측정한다. 선택 분포와 갱신 주기를 기록한다.
- [ ] 환경별 풀 고정 등 최적화를 선택하면 학습 전체의 다양성이 충분한지 입증한다. 일부 환경의 제한을 전체 8종 가용성으로 잘못 보고하지 않는다.
- [ ] 부분 reset은 지정된 환경만 변경하며 seed·호출 방식이 같을 때 재현되도록 한다.
- [ ] 물체 수 커리큘럼 Gray 1~4 / White 1~5는 유지한다. 이는 형상 선택·크기·reset 방식과 별개다.

## 3. 관측 순서

메인 변경은 **조인트 → 엔드 이펙터 자세 → 타겟 위치 → 목표 → 저번 액션 → 센서 데이터 → 장애물** 순서다. 앞선 명시적 요구인 실제 Arm 값, Hand 2D, 16개 장애물 슬롯은 유지하되 추가 관측을 임의로 늘리지 않는다.

| 순서 | 항목 | 차원 | 조건 |
| --- | --- | --- | --- |
| 1 | Arm Joint | 12 | 실제 관절 위치 6 + 속도 6, default 값 차감 제거 |
| 2 | Hand Joint | 2 | 기존 관절 기반 개방도 유지 |
| 3 | EEF Pose | 7 | 위치 3 다음 quaternion 4 |
| 4 | 타겟 위치 | 3 | 공통/Actor는 기존 초기 위치, Critic의 현재 위치는 별도 유지 |
| 5 | 목표 | 2 | 기존 초기 타겟 기준 거리·방향 |
| 6 | 이전 행동 | 8 | 기존 tanh 변환된 행동 피드백 |
| 7 | 텍타일 | 17 | 기존 접촉 비트 |
| 8 | F/T | 6 | 기존 보상된 Wrench |
| 9 | 장애물 | 16×4=64 | `[Mask,x,y,z]`, 미사용 슬롯 0 |

EEF 위치·자세를 하나의 Term으로 통합할 필요는 없다. 연결 순서만 지키며 4×4 행렬 16D로 바꾸지 않는다. policy 57D slice는 Arm `0:12`, Hand `12:14`, EEF `14:21`, 초기 타겟 `21:24`, 목표 `24:26`, 행동 `26:34`, 텍타일 `34:51`, F/T `51:57`이다. 끝 인덱스는 제외한다.

- [ ] 선언 순서뿐 아니라 실제 연결 순서·모델 처리 순서를 확인한다. 비영 기본 관절값으로 Arm 값 차감 제거를 확인한다.
- [ ] 장애물 20→16슬롯·80→64D 변경을 버퍼·인코더·차원 검사에 반영한다. 16은 관측 용량이며 실제 장애물 수를 늘리는 조건이 아니다. 초과 설정을 조용히 잘라내지 않는다.
- [ ] Actor 원시 입력 121D(57+64), Critic 124D(57+3+64)를 확인한다. 임베딩 16D 유지 시 본체 입력 73D/76D는 유지된다. 기존 체크포인트의 입력 순서·차원 호환성을 자동 보장하지 않는다.

## 4. Actor와 Critic의 의미 있는 관측 차이

| 항목 | Actor | Critic |
| --- | --- | --- |
| 타겟 | 기존 초기 위치 | 공통 관측 외 **현재 타겟 XYZ 3D** 유지 |
| 장애물 위치 | 기존 초기 관측 캐시 | **매 관측 시 현재 위치** |
| 장애물 대상 | 기존 초기 가시성·관측 오류 규칙 | 가림 여부와 무관하게 **실제 장면에 배치된 모든 장애물** |
| 형식·좌표 | `[Mask,x,y,z]`, 16슬롯, 로봇 root 좌표 | 동일 |

**실제 배치된 물체**는 이번 장면의 장애물 역할로 성공적으로 배치되어 활성화된 물체를 뜻한다. 사전 생성만 된 후보, 주차·격리 물체, 배치 실패 슬롯은 물리적으로 어딘가에 존재하더라도 Critic 관측 대상이 아니다. 위치가 선반 근처인지 여부만으로 활성 여부를 추측하지 않고 배치 결과·역할 mapping·active mask를 일치시킨다. 에피소드 중 실제 장애물이 움직여도 현재 위치를 계속 관측한다. 타겟은 기존 현재 타겟 3D로 제공하며 장애물 슬롯에 중복 포함하지 않는다.

Critic은 가시성 필터와 1% 비트 반전을 적용하지 않는다. 실제 활성 장애물의 Mask=1, 비활성·미사용 슬롯은 Mask와 XYZ 모두 0이다. Actor는 초기 가시성 판정·1% 반전·캐시를 유지한다. 두 인코더는 별도 가중치를 유지한다. 이전 요구인 왼쪽→오른쪽(Y 내림차순) 정렬과 유효 인접 슬롯의 10% 순서 교환도 유지한다. Critic 좌표 노이즈와 순서 교환 재추출 주기는 아직 미확정이며 구현 시 명시한다.

- [ ] Actor 초기 캐시와 Critic 현재 장애물 그룹을 분리하고 현재 정보를 Actor/export로 전달하지 않는다.
- [ ] 가려진 실제 장애물이 Critic에 포함되는지, 장애물 이동 시 Critic만 갱신되는지, 미사용 물리 후보는 항상 제외되는지 확인한다.
- [ ] 역할 전환·부분 reset 후 Mask·좌표·센서·관측 그룹이 동일 물체를 가리키는지 확인한다. rollout 저장·모델 입력·gradient 연결·zero padding을 검사한다.

## 5. 적용할 배치 알고리즘: OBB 기반 텐서 배치

사용자가 지정한 결과는 [gallery.png](../../../outputs/bbox_scene_layout/gallery.png), [benchmark.json](../../../outputs/bbox_scene_layout/benchmark.json), [gallery.npz](../../../outputs/bbox_scene_layout/gallery.npz)다. 그림과 보고서를 확인했으며, 연결된 구현은 [bbox_scene_layout.py](../../../src/inspire_sweep_baseline/inspire_sweep_baseline/mdp/common/bbox_scene_layout.py)의 **`LayoutConfig` / `generate_layout`**이고 생성 도구는 [benchmark_bbox_layout.py](../../../src/inspire_sweep_baseline/scripts/benchmark_bbox_layout.py)다. 이 독립 모듈의 기하 계약을 기준으로 v0_2에 연결하며 v0_2_1의 reset 구현은 참고하지 않는다.

앞서 문서에 적었던 `src/scene_randomization/generator.py`의 `wrist_downward_v2`는 **원통 중심 기반 선행 알고리즘**이다. 전면 손목 점유라는 배경은 공유하지만 이번에 적용할 OBB 알고리즘과 다르다. 원통의 24×8 방향·거리 스케줄, 16각형 손가락 접근 경로, 셀 밀도·뒤쪽 최소 개수 규칙을 이번 배치에 자동 이식하지 않는다.

대략적인 동작은 다음과 같다.

1. 최종 크기와 yaw가 반영된 각 물체의 **회전 바운딩 박스(OBB)**를 만든다. 비대칭 bounds의 중심 offset을 반영하여 asset root와 배치용 중심을 변환한다.
2. 주어진 타겟 시작·목표 OBB 사이의 직선 이동 영역을 만들고, 로봇 진입 전면인 board −Y 방향까지 확장해 **RED** 금지 영역을 만든다. 타겟 yaw는 이동 중 일정하다고 가정한다.
3. RED 바깥을 **65 mm** 확장한 영역과 밀기 반대편 접근 직사각형을 합치고 RED를 제외해 **Gray**를 만든다. **White**는 RED·Gray와 겹치지 않는 영역이다. 장애물 중심뿐 아니라 **박스 전체**로 검사하므로 모서리라도 RED에 침범하면 거절한다.
4. 분리축 정리(SAT)로 존·박스 간격을 검사하며 후보 위치와 yaw를 추출한다. 현재 모듈의 기본 물체 간격 20 mm, 경계 여유 5 mm를 기준으로 실제 scale된 물체 전체가 작업판 안에 있는지 확인한다.
5. 제한된 후보·restart·pass 안에서 여러 배치를 탐색한다. 기본 예산은 32후보×4 restart×2 pass다. 실패 슬롯을 재시도하고, 총 배치 수가 가장 많은 restart를 선택한다. 동률이면 Gray 수가 많은 결과를 선택한다. 타겟·목표·간격을 바꾸어 억지로 채우지 않는다.
6. `centers`, `yaw`, **`active`**, `requested`, `actual`, `complete`를 반환한다. 요청보다 적게 배치될 수 있으며 `complete=False`는 탐색 예산 내 미충족을 뜻한다. **비활성 슬롯 좌표 0은 스폰 위치가 아니다.** 실제 활성 슬롯만 스폰·관측·보상에 연결한다.

참고 그림과 benchmark는 **Gray 패딩 60 mm** 결과다. 업데이트에서는 **`gray_padding=0.065` 고정**으로 변경하고 `obstacle_gray_zone_padding` 및 관련 fraction 커리큘럼 연결을 삭제한다. RED는 축소하지 않는다. 장애물 개수 커리큘럼 Gray 1~4 / White 1~5는 유지한다.

단위는 m이고 기본 board는 X=[−0.5,0.5], Y=[0,0.4]다. 기존 선반 좌표에서 board 좌표는 `(shelf_y, 0.20-shelf_x)`, yaw는 `shelf_yaw-pi/2`다. OBB 생성기는 타겟·목표를 입력으로 받으므로 원통 생성기의 명령 분포를 새 요구로 추가하지 않는다. 별도 변경이 없는 타겟·목표 명령 조건은 v0_2를 기준으로 확인한다.

- [ ] 모든 iteration에서 Gray 패딩 65 mm와 패딩 커리큘럼 제거를 확인한다. 최종 크기의 실제 bounds·중심 offset·좌표축 변환을 검증한다.
- [ ] 존·경계·간격·부분 배치·불가능 슬롯·0개 요청·부분 reset을 최종 물리 pose 기준으로 재검사한다. 배치 시각화와 실제 스폰이 일치해야 한다.
- [ ] OBB 검사는 2D 기하이며 손·팔의 3D 운동학·마찰·전도·스폰 안정성을 입증하지 않는다. 저장 benchmark도 layout search만 측정하며 실제 2048 env 동작을 입증하지 않는다.

## 6. 성공 반경 3 cm와 Goal Hold 외곽 8 cm

성공 인정 조건은 XY 거리 **`d <= 0.03 m`**로 완화한다. Goal Hold는 `position_tolerance=0.03`, `outer_radius=0.08`로 변경한다. 기존 연속 함수에서 `d < 0.08 m`이면 양의 Hold 보상을 받을 수 있고 **정확히 8 cm에서는 0**이다. 속도 감쇠와 weight 8.0은 유지한다.

**성공 인정 XY 반경을 직접 또는 간접적으로 사용하는 모든 보상·터미네이션·커리큘럼 및 관련 로직에 3 cm를 빠짐없이 반영한다.** 특정 성공 함수나 Hold 설정만 바꾸는 것으로 완료하지 않는다. 성공 반경을 사용하는 보상 분기·정규화·목표 점유 판정, 성공/실패 종료 분할, timeout 보너스, 커리큘럼의 초기값·중간값·최종값·갱신 함수, 평가·성공률 로그·시각화·테스트까지 참조 경로를 대조한다. 성공 여부의 경계는 모두 `d <= 0.03 m`로 일치시킨다.

- [ ] 적용 대상 환경의 설정 상속·함수 기본 인자·상수·캐시·실행 중 갱신을 포함하여 성공 XY 반경의 모든 사용처를 목록화한다. 남아 있는 `0.02`/2 cm 조건이 성공 반경 용도인지 확인하고 해당 용도는 3 cm로 변경한다. 물체 간격 등 무관한 2 cm 값은 일괄 치환하지 않는다.
- [ ] 커리큘럼이 성공 반경을 2 cm 또는 다른 값으로 되돌리지 않도록 한다. 비활성 일정은 활성화하지 않고, 반경을 갱신하는 연결이 있으면 제거하거나 전 구간 3 cm를 유지하도록 정리한다. 시작·일정 경계·최종 iteration 및 reset 후 실제 적용 반경을 검사한다.
- [ ] 반경 공유 설정과 각 소비 함수의 실제 값을 대조하고, 동일한 XY 거리 입력에 대해 모든 성공 판정 경로가 3 cm 안/같음/밖에서 일치하는지 검증한다. 보상 함수 고유의 연속 점수 형태와 Hold 외곽 8 cm는 성공 반경과 구별한다. 다른 버전·공통 부모의 동작을 의도 없이 바꾸지 않는다.

- [ ] 성공·실패 timeout 분할, 성공률 기록, 목표 반경 표시, Hold 내부 반경을 일치시킨다. v0_2의 timeout 보너스 +30을 유지하되 새 3 cm 성공 경계를 포함하도록 한다. 목표 도달 즉시 종료나 유지시간 조건을 추가하지 않는다.
- [ ] 3 cm 안/같음/밖, Hold 3 cm 연결부와 8 cm 경계의 값을 검증한다.

## 7. 실제 접촉 AND 고정 EEF 높이 조건

접촉 보상은 **실제 타겟–손 접촉 AND EEF Frame 중심 높이 < 고정 임계값**일 때만 지급한다. 기존 fresh·finite·접촉력 norm `>=0.01 N`, weight 1.45는 유지하고 v0_2의 목표 점유 OR 조건을 제거한다. 장애물·선반 접촉만으로 이 타겟 접촉 보상을 주지 않는다. 높이가 임계값과 같거나 비유한 경우는 통과하지 않는다.

EEF 기준은 [Final Scene](../../../src/inspire_sweep_baseline/inspire_sweep_baseline/assets/scenes/final.py)의 `ee_frame` / `end_effector`, `target_pos_w[:,0]`다. 현재 axia80_link로부터 local Z offset은 `0.13 + 0.0254/2 = 0.1427 m`이다. 손목 원점이나 손가락 끝과 혼동하지 않고 화면과 실제 Frame 위치를 확인한다.

**임계값은 최종 크기 기준 물체들의 평균 윗면 높이를 출발점으로 한 고정값**이다. 개별 타겟의 종류·scale·현재 자세를 따라 바꾸지 않는다. 이전의 작업면 위 125 mm / 기본 Z=1.175 m는 YCB `size_fraction=1.0`과 균등 가정을 사용한 잠정치였으므로 **이번 중앙 크기 정정 이후 확정값으로 사용하지 않는다.** 최종 8종 bounds와 크기 분포를 확인해 평균을 다시 계산하고, 실제 손 형상과 접근 자세 검증을 거쳐 하나의 고정값을 정한다.

- [ ] EEF 높이를 초기 선반 작업면 기준 수직 높이로 비교하고 환경별 origin Z를 보정한다. 타겟 이동·기울기나 에피소드 중 선반 이동에 따라 문턱을 갱신하지 않는다.
- [ ] **너무 낮아 손이 바닥과 충돌해야만 보상을 받는 조건이 되지 않는지**, 모든 8종·크기 범위에서 안전한 측면 접촉 자세가 가능한지 검사한다.
- [ ] **너무 높아 위에서 누르는 접촉이 계속 인정되지 않는지** rollout에서 검사한다. 평균값이 모든 물체의 개별 윗면보다 낮다는 뜻은 아니므로 기하·동작 검증 없이 값을 확정하지 않는다.
- [ ] 접촉 유무×높이 미만/같음/초과, stale·비유한 값·origin Z 차이를 검사한다. 선택한 고정값·평균 산출 근거·바닥 여유·상부 누르기 검사 결과를 기록한다. 이 단일 높이 조건만으로 모든 상부 누르기를 방지한다고 주장하지 않는다.

## 8. 스폰·시각화·물리 물체 수 및 2048 env 점검

사용자가 보고한 v0_2_1의 문제는 **허공 스폰 후 상호 충돌·발사**, **비타겟 물체에 타겟 bbox 시각화 적용**, **과도한 사전 등록으로 2048 env 실행 불가**다. 이번 작업은 보고를 기록한 것이며 원인 재현·진단을 완료한 것은 아니다. 해당 구현을 재사용하지 않고 v0_2 기반 업데이트의 재발 방지 검사로 삼는다.

**예방적 주의사항:** 위 오류는 사용자가 **v0_2_1에서 발생한 것으로 파악한 사례**이며, 기준 환경 v0_2에도 같은 오류가 존재한다고 단정하는 것은 아니다. 다만 이번 업데이트에서 형상·크기·역할·스폰 방식을 변경하면서 유사 문제가 생길 가능성을 놓치지 않도록, **해당 증상이 현재 재현되지 않더라도 아래 점검을 구현·검증의 필수 항목으로 수행한다.** 스폰 방식 자체는 특정하지 않지만, 공중 중첩 스폰으로 인한 충돌·발사, 비타겟의 타겟 bbox 표시, 불필요한 물리 후보 사전 등록으로 인한 2048 env 실행 장애가 발생하지 않도록 설계한다. 다른 버전에서 보고된 문제라는 이유로 검사를 생략하지 않으며, v0_2_1 구현을 참고하지 않는 원칙은 유지한다.

- [ ] 첫 생성과 전체/부분 reset의 순서를 점검한다. 형상·scale·role·pose·속도·중력·센서 mapping을 일관되게 갱신하고, 중첩되거나 미완성인 중간 상태에서 물리 step이 실행되지 않도록 한다.
- [ ] 활성 물체는 최종 bounds의 최저점을 작업면에 맞춘다. 모든 활성 물체 쌍·선반과의 초기 침투와 과도한 높이, 비정상 초기 선속도·각속도, 초기 몇 step의 튀어오름·발사를 검사한다.
- [ ] 미사용 후보가 필요한 구현이라면 active=false가 물리 충돌 비활성화를 뜻한다고 가정하지 않는다. 후보끼리·활성 물체·다른 환경과 충돌하거나 낙하하지 않도록 실제 격리를 검증한다. 주차 좌표를 장애물 관측에 포함하지 않는다.
- [ ] 타겟 bbox 시각화는 **현재 선택된 실제 타겟에만** 적용한다. reset·역할 변경 시 이전 표시를 제거하고 새 target ID·pose·bounds와 일치시킨다. 배치 알고리즘이 모든 물체에 내부 bbox를 사용하는 것과 화면의 타겟 표시를 구별한다.
- [ ] 물리 body·collider·센서·사전 후보 수와 메모리를 최적화한다. 활성 상한은 타겟 1+Gray 4+White 5=10개지만 사전 등록 수를 임의의 숫자로 확정하지 않는다. 모델·mesh 데이터 공유와 실제 물리 body 수 감소를 구분하여 측정한다.
- [ ] **2048 env에서 실제 초기화·반복 전체/부분 reset·rollout을 실행**해 OOM, PhysX 용량 오류, 비정상 충돌·발사, 미사용 후보의 관측 유입, 타겟 표시 오류를 확인한다. GPU 모델·VRAM·설정·물리 수·peak 메모리·초기화/reset 시간·처리량을 기록한다. `scripts/train.py` 기반 짧은 학습 smoke 검증도 포함하고, 장기 학습 성능과 구별한다.
- [ ] 실행 장비 제약으로 2048 env를 검증하지 못하면 미검증으로 남긴다. 소규모 실행이나 순수 배치 benchmark 통과를 2048 env 성공으로 대체하지 않는다. 성능을 위해 종류·크기·배치 다양성을 몰래 줄이지 않는다.
